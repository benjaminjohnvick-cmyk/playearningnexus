Add now — Payments

to add Stripe + PayPal · 1 flag

The one remaining set of real keys. Card checkout and payouts stay off until these are set and the flag is flipped.

Two gates before you turn this on. Money-out is a permanent compliance line — clear it with your lawyer first. And these are payment credentials, so you enter them yourself — they should never be handled by anyone else.
# Payments — Railway raw block 
# Stripe — dashboard.stripe.com (Live mode)
STRIPE_SECRET_KEY=sk_live_REPLACE_ME
STRIPE_WEBHOOK_SECRET=whsec_REPLACE_ME
# PayPal — developer.paypal.com
PAYPAL_CLIENT_ID=REPLACE_ME
PAYPAL_SECRET=REPLACE_ME
# sandbox while testing, then flip to live:
PAYPAL_ENV=sandbox
# needed for PayPal return/cancel redirects + optional payout receiver:
PUBLIC_SITE_URL=https://yourdomain.com
PAYPAL_BUSINESS_EMAIL=you@business.com

Survey providers — supply networks

1 live · 10 ready 11 networks · more supply = more earning hours

The member survey wall is fed by a multi-provider supply registry (survey-providers.ts). BitLabs is live at launch; the other ten are wired and dormant. Each network's enable flag (PROVIDER_<NAME>_ENABLED) defaults on, so a provider auto-activates the moment its API key is set — no flag flip needed. To hold one off even with a key present, set its flag to 0. Keys live in env/DB, never in a URL.

These are revenue, not cost. Survey networks pay you rev-share on completed surveys — adding keys turns on more inventory (more surveys available to members), it doesn't add a bill. Onboarding each one means applying as a publisher and getting approved.

Custom domain & deploy

go-live put the app on your own domain, then redeploy

The app is already deployed on Railway and live at its .up.railway.app URLs (frontend service getgreen, backend service playearningnexus, project passionate-presence). All services auto-deploy on every push to GitHub main. To put it on your own domain: register the domain, point it at Railway, then switch the domain-aware env vars over.

You do the purchase and DNS. Registering a domain is a purchase, and DNS records are changed at your registrar — those two steps are yours to do (I don't buy domains or change your registrar settings). Everything else is Railway + env vars.

Once the domain is live, set these so redirects, links, media, and CORS use it instead of the Railway URLs:

# Domain env vars — Railway raw block 
# Set on the BACKEND (playearningnexus) service once your domain is live:
PUBLIC_SITE_URL=https://www.yourdomain.com
APP_URL=https://www.yourdomain.com
FRONTEND_URL=https://www.yourdomain.com
# was * (open) — lock CORS to your domain in production:
CORS_ORIGIN=https://www.yourdomain.com
# only if you gave the BACKEND its own domain (api.yourdomain.com):
BACKEND_URL=https://api.yourdomain.com
# R2 media playback — swap off the rate-limited r2.dev to your CDN domain:
HLS_PLAYBACK_BASE_URL=https://media.yourdomain.com
# Set on the FRONTEND (getgreen) service — points the site at the backend:
VITE_NEXUS_API_URL=https://api.yourdomain.com

Last step — verify with the self-test

In the admin app, run the provisioningSelfTest function. It pings each provider with a free verify call and returns green / red per key — including whether EMAIL_FROM is a verified sender — so you know a key actually works instead of waiting for a feature to break. Anything red comes with the exact fix.
